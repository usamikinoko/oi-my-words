# HTTP 缓存到底怎么生效

打开任何一个网页，开发者工具里总能看到 (from disk cache) 或者 304 这样的字样。它们背后就是 HTTP 缓存。HTTP 缓存是 Web 世界里最不起眼却又最关键的优化手段：没有它，每次刷新页面都要把图片、脚本、样式重新下载一遍；有了它，绝大多数重复请求根本不走网络。这篇文章就从头到尾讲清楚，HTTP 缓存到底是怎么生效的。

## 一、缓存是什么，为什么需要它

简单说，缓存就是把已经拿到的数据"存起来"，下次需要的时候直接取用，省去重复劳动。HTTP 缓存特指浏览器（以及中间的网络代理、CDN 节点）把服务器返回的响应保存下来，在合适的时机直接复用。

它的价值体现在三个层面：省流量，图片、脚本这些静态资源不用反复下载；省时间，本地读取比网络往返快几个数量级；省服务器压力，大量重复请求根本到不了服务器，后端负载大幅下降。据互联网公司公开的数据，开启合理缓存后，静态资源类的重复请求命中率常常能达到 90% 以上。

## 二、缓存的"仓库"都设在哪里

要理解缓存的生效过程，先要知道缓存可能存在于哪些环节。按离用户的远近，大致有四层：

1. 浏览器内存缓存（memory cache）：存在浏览器进程内存里，读取最快，但页面关闭或进程退出就没了。

2. 浏览器磁盘缓存（disk cache）：存在硬盘上，跨会话保留，容量大但读取稍慢。开发者工具里的 (from disk cache) 就是它。

3. 代理服务器缓存：公司或运营商的代理节点，为多用户共享缓存。

4. CDN 边缘节点缓存：离用户最近的服务器缓存，是大型网站静态资源加速的主力。

浏览器寻找缓存的顺序，大致是"先内存、后磁盘"。命中内存缓存时网络面板显示 (from memory cache)，命中磁盘缓存时显示 (from disk cache)。另外，Service Worker 也可以作为独立的缓存层，由代码主动控制，这里先按下不表。

## 三、强缓存：连服务器都不问

HTTP 缓存按"要不要询问服务器"分为两大类。第一类是强缓存（强缓存 / Strong Cache），特征是：命中后根本不发请求，直接使用本地副本，网络面板显示 (from disk cache) 或 (from memory cache)，状态码是 200。

强缓存的"寿命"由响应头决定，主要有两个字段：

- `Cache-Control: max-age=31536000`：现代 HTTP 的推荐方式，单位是秒，表示资源在 31536000 秒（一年）内可以直接复用。

- `Expires: Wed, 21 Oct 2026 07:28:00 GMT`：HTTP/1.0 时代的老字段，给出一个绝对过期时间。因为依赖客户端时钟，容易受本地时间不准影响，现在基本被 Cache-Control 取代；两者同时出现时，`Cache-Control` 优先。

强缓存生效的判断极其简单：把资源"出生时间"加上 max-age，如果当前时刻还没到这个时间点，就直接用缓存，全程零网络交互。正因如此，强缓存的代价也很明显：只要在有效期内，服务器更新了资源，客户端也看不到。这就引出了第二类缓存。

## 四、协商缓存：带着"信物"去问问服务器

第二类是协商缓存（Conditional Cache / 协商缓存），特征是：请求照发，但带上资源的"指纹"，服务器比对后如果发现资源没变，就返回一个轻量级的 304 Not Modified 响应（没有响应体），浏览器继续使用本地副本；如果变了，就返回 200 和新内容，浏览器用新内容替换旧缓存。

协商缓存需要"指纹"字段来比对，核心是这两对：

- `ETag` 与 `If-None-Match`：ETag 是服务器为资源生成的唯一标识（通常是内容哈希或版本号）。浏览器再次请求时带上 If-None-Match: <etag值>，服务器拿它和当前资源的 ETag 比对，一致则返回 304。

- `Last-Modified` 与 `If-Modified-Since`：Last-Modified 是资源的最后修改时间，再次请求时通过 If-Modified-Since 带上。因为时间粒度是秒级、且可能被中间环节改写，准确性不如 ETag，所以实际中 ETag 优先级更高，两者都带时服务器先比对 ETag。

一句话总结两种缓存的关系：强缓存是"免检"，协商缓存是"复检"。免检期内直接放行；过了免检期，进入复检，用一次轻量请求确认资源是否仍然有效。

## 五、完整的一次缓存流程

把前面几节串起来，浏览器处理一次资源请求的逻辑是这样的：

1. 检查本地缓存：没有缓存或缓存已过期，走第 4 步；有未过期的缓存，进入第 2 步。

2. 强缓存命中：直接使用本地副本，返回 200，不发任何请求，流程结束。

3. 强缓存未命中（已过期或 Cache-Control 要求复检）：带上 If-None-Match / If-Modified-Since 发请求。

4. 服务器比对指纹：资源未变，返回 304，浏览器续用本地缓存（并刷新它的有效期）；资源已变，返回 200 + 新内容，浏览器更新缓存。

可以看出，一次成功的缓存利用，最多只产生一次极小的 304 往返，绝大多数情况连往返都没有。这也是为什么性能优化建议里总是强调"给静态资源设置足够长的 max-age + 变化时更换 URL"。

## 六、你的操作在缓存里意味着什么

缓存机制不仅由服务器决定，用户（或浏览器的）操作也会影响它的生效路径。理解这些行为，排查问题时能少走弯路：

- 地址栏输入网址、回车或前进后退：浏览器通常会按缓存规则正常命中，强缓存直接生效。

- 普通刷新（F5）：浏览器一般会携带 Cache-Control: max-age=0 之类的请求头，相当于"强缓存别用了，去协商一下"，于是大多走 304；但不会完全绕过协商缓存。

- 强制刷新（Ctrl+F5 / Cmd+Shift+R）：浏览器带上 Cache-Control: no-cache，要求沿途所有缓存节点都回源验证，304 都可能被跳过，直接拿 200 新内容。

- 隐身模式：多数浏览器会禁用磁盘缓存，只保留内存缓存，因此刷新后常常重新下载资源。

Vary 字段也是容易忽略的一环。服务器用 Vary: Accept-Encoding 告诉缓存"不同编码的版本要分开存"，否则压缩版和未压缩版会互相覆盖。CDN 场景下，凡是响应内容会随请求头变化的，都应该用 Vary 声明，否则缓存可能"张冠李戴"，把给手机端的版本发给 PC 用户，这是很多移动端兼容问题的隐藏来源。

Service Worker 缓存则代表了另一条思路：它由网页代码主动注册，拦截所有请求，可以自行决定"命中缓存、走网络还是两者同时"，还能实现离线访问。它不是 HTTP 协议层的缓存，而是应用层自己搭的"私人仓库"，常与 HTTP 缓存叠加使用。

## 七、写在最后

HTTP 缓存并不神秘，它无非回答三个问题：能不能缓存、缓存多久、过期了怎么确认。Cache-Control 管前两个，ETag 等条件头管第三个。掌握这套机制，你就能解释开发者工具里那些 (from disk cache) 和 304 从何而来，也能在设计接口和静态资源时，主动规划出既省流量又不至于"更新失灵"的缓存策略。下次遇到"改了代码没生效"的灵异事件，先别急着骂浏览器，打开网络面板看看——多半是缓存机制在按它自己的规则勤恳工作。
