# HTTP 缓存到底怎么生效

## 一、缓存为什么值得认真对待

### （一）缓存的三重收益

打开任何一个网页，开发者工具里总能看到 (from disk cache) 或者 304 这样的字样。它们背后，正是 HTTP cache（HTTP 缓存）在起作用。

没有它，每次刷新页面，图片、脚本、样式都要重新下载一遍；有了它，绝大多数重复请求根本不走网络。cache（缓存）的意义，是把已经拿到的数据先存起来，下次需要时直接取用。它的价值落在三个层面：省流量，静态资源不必反复下载；省时间，本地读取比网络往返快几个数量级；省服务器压力，大量重复请求根本到不了服务器。在大型网站的实践中，这类重复请求的命中比例往往很高，缓存配置的收益正体现在这里。

### （二）缓存分布在哪些环节

要理解缓存的生效过程，先要知道缓存存在于哪些环节。按离用户的远近，大致有四层。memory cache（内存缓存）位于浏览器进程的内存中，读取最快，页面关闭或进程退出后即消失。disk cache（磁盘缓存）存放在硬盘上，可跨会话保留，容量较大而读取稍慢，开发者工具里的 (from disk cache) 指的就是它。再往外，公司或运营商的代理服务器为众多用户共享同一份缓存，CDN 的边缘节点缓存离用户最近，是大型网站静态资源加速的主力。

浏览器寻找缓存的顺序，大致是先内存、后磁盘，网络面板里的 (from memory cache) 与 (from disk cache) 分别对应这两者。此外，Service Worker 也能充当独立的缓存层，由代码主动控制，这一点后文再提。

## 二、强缓存免检放行

### （一）有效期由响应头决定

HTTP 缓存按是否询问服务器，分为两大类型。第一类称为 Strong Cache（强缓存），其特点是命中之后根本不发请求，直接使用本地副本，网络面板显示 (from disk cache) 或 (from memory cache)，状态码为 200。

强缓存的寿命由响应头决定，主要涉及两个字段。Cache-Control: max-age=31536000 是现代 HTTP 的推荐写法，单位是秒，表示资源在 31536000 秒（约一年）内可以直接复用。Expires: Wed, 21 Oct 2026 07:28:00 GMT 是 HTTP/1.0 时代的老字段，给出绝对的过期时间。它依赖客户端时钟，容易受本地时间不准的影响，如今基本被 Cache-Control 取代；两者同时出现时，以 Cache-Control 为准。

### （二）免检期内的代价

强缓存的判断逻辑非常简单，无非是把资源的"出生时间"加上 max-age，只要当前时刻尚未越过这个时间点，就直接使用缓存，全程没有网络交互。

代价也同样直白。只要还在有效期内，即便服务器更新了资源，客户端也看不到，于是就有了第二类缓存。

## 三、协商缓存复检确认

### （一）指纹字段的比对方式

第二类称为 Conditional Cache（协商缓存），其特点是请求照发，但会带上资源的"指纹"。服务器比对指纹之后，若资源没有变化，就返回一个没有响应体的轻量级 304 Not Modified；若资源已经变化，则返回 200 与新内容，浏览器用新内容替换旧缓存。

协商缓存的比对依靠两对"指纹"字段。ETag 与 If-None-Match 是一对，ETag 是服务器为资源生成的唯一标识，通常来自内容哈希或版本号，浏览器再次请求时携带 If-None-Match: <etag值>，服务器比对一致则返回 304。Last-Modified 与 If-Modified-Since 是另一对，记录资源的最后修改时间。由于时间粒度只有秒级，且可能被中间环节改写，其准确性不如 ETag，实际使用中 ETag 的优先级更高，两者同时出现时服务器先比对 ETag。

### （二）免检与复检的衔接

两种缓存的关系，不妨概括为一句话：强缓存是"免检"，协商缓存是"复检"。免检期内直接放行；免检期过后进入复检，用一次轻量请求确认资源是否仍然有效。

于浏览器而言，一次成功的缓存利用，最多只产生一次极小的 304 往返，多数情况下连这次往返都可以省去。这正是性能优化建议总强调"给静态资源设置足够长的 max-age，资源变化时更换 URL"的原因。

## 四、一次请求的完整流程

### （一）四步决策

把前文串起来，浏览器处理一次资源请求的逻辑可以概括为四步。第一步检查本地缓存，若无缓存或缓存已过期，转入第四步；若存在未过期的缓存，进入第二步。第二步，强缓存命中，直接使用本地副本，返回 200，不发任何请求，流程结束。

第三步，强缓存未命中，携带 If-None-Match 与 If-Modified-Since 发出请求。第四步，服务器比对指纹，资源未变则返回 304，浏览器续用本地缓存并刷新其有效期；资源已变则返回 200 与新内容，浏览器更新缓存。

## 五、Vary 与 Service Worker

### （一）Vary 的作用

Vary 字段，实则也常被人忽略。服务器用 Vary: Accept-Encoding 告诉缓存"不同编码的版本要分开存放"，否则压缩版与未压缩版会互相覆盖。

CDN 场景下，凡是响应内容随请求头变化的，都应当用 Vary 声明，否则缓存可能把给手机端的版本发给 PC 用户。这是很多移动端兼容问题的隐藏来源。

### （二）Service Worker 缓存

Service Worker 缓存则代表了另一条思路。它由网页代码主动注册，可以拦截所有请求，自行决定命中缓存、走网络，还是两者同时进行，还能实现离线访问。

它不是 HTTP 协议层的缓存，而是应用层自己搭建的"私人仓库"，常与 HTTP 缓存叠加使用。

## 六、写在最后

HTTP 缓存并不神秘，它始终在回答三个问题：能不能缓存、缓存多久、过期之后如何确认。Cache-Control 回答前两个，ETag 等条件头回答第三个。

掌握这套机制之后，我们就能解释开发者工具里那些 (from disk cache) 与 304 从何而来，也能在设计接口与静态资源时，主动规划出既省流量又不至于"更新失灵"的缓存策略。下次再遇到"改了代码没生效"的灵异事件，先别急着怪浏览器，打开网络面板看一看，多半是缓存机制在按自己的规则勤恳工作。
